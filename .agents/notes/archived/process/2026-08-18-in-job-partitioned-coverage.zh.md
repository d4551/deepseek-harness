# Agent Note: 单 job 分区覆盖率

Status: implemented
Archived: 2026-09-16

[English](2026-08-18-in-job-partitioned-coverage.md) | 中文

## 问题

原生 Windows 覆盖率是拉取请求完整清单中反馈最慢的路径。把插桩套件保留在单个 Vitest 进程内并只使用 1 个 worker，可以避开较大进程内 worker 池曾出现的 worker 丢失和 Node 24 CJS lexer 故障，但一次失败可能超过 14 分钟才会显现，而且门禁调度器会在子进程结束前扣住输出。

分区必须保留全部测试以及每项失败结果。把子进程保留在一个覆盖率 job 内，可以避免重复 checkout、安装、产物传输和额外的合并 job。

## 决策

协调器保留为显式选择的执行模式。[完整源码质量门禁](../testing/2026-09-16-complete-source-quality-gates.zh.md)取代本文仅在合并时检查阈值的规则及默认 CI 分区配置。Linux 与原生 Windows CI 在一次插桩 Vitest 调用中运行完整套件。`DSH_COVERAGE_MAX_WORKERS` 为该调用提供全部 worker 预算；不存在独立的无插桩门禁。

调用方将 `DSH_COVERAGE_PARTITIONS` 设为大于 1 的整数时，[门禁调度器](../../../../scripts/run-gates.ts)选择分区命令。[协调器](../../../../scripts/coverage-partitions.ts)并发启动相应数量的 Vitest 子进程，每个进程拥有 1 个 worker、独立分片、自己的覆盖率目录和一份 blob 报告。每个子进程保留配置中的报告器，以及逐文件的语句、分支、函数与行阈值。

协调器等待全部子进程结束，验证 blob 目录只包含预期文件，然后运行一次合并覆盖率报告。每个子进程与合并步骤都必须通过。某个分片可能没有覆盖由其他分片执行的源码；即使合并报告完整，也不能把该子进程的阈值失败变成成功。因此，分区不适合作为默认的完整源码覆盖率门禁。

## 失败与输出语义

分区子进程通过协调器流式传递 stdout 与 stderr。覆盖率门禁启用调度器流式输出，使 CI 实时收到进度。协调器为每个子进程保留一份有界的 64 KiB 混合输出尾部，并在验证完整 blob 集合前将其与 spawn 错误、退出码或信号一并重印。

普通测试失败仍可产出 blob，使合并步骤可以先报告覆盖率，再由协调器返回失败。spawn 失败、信号终止、非零退出、blob 缺失或多余，以及合并失败都会让门禁失败。清理操作只 unlink 呈链接形态的覆盖率路径，不会递归跟随其目标。

## 验证

分区测试验证子进程与合并步骤的完整参数、包脚本分隔符移除、单 worker 子进程、失败测试合并、blob 校验前的失败诊断、spawn 失败后等待兄弟进程，以及链接安全清理。调度器测试验证显式分区选择、非法数量拒绝、Windows 构建依赖、完整 worker 预算分配、具有阻断性的结果和流式输出。CI 工作流测试要求 Linux 与 Windows 覆盖率 job 不设置分区选项。

历史原生 Windows 对比中，双分区耗时约 405 秒，16 分区耗时 112.66–122.01 秒；两个 Linux 样本的双分区耗时为 276.68 秒和 282.27 秒。这些测量采用较早的覆盖率清单和阈值策略，不能证明完整源码覆盖率的性能或通过结果。

## 曾考虑的替代方案

**工作流级分片。** 独立 job 会重复设置工作，并需要产物传输和合并依赖。协调器把进程隔离保留在一个 job 和工作区内。

**在一个插桩进程内增加 worker。** 历史 Windows 试验在较高扇出下暴露了 worker 退出、fixture（测试前置数据）不稳定和 Node 24 CJS lexer 故障。独立的单 worker 子进程提供另一层隔离；完整套件 CI 仍需基于当前清单进行测量。

**仅在合并时检查阈值。** 原设计避免独立判定分片的部分执行。完整源码质量门禁决策撤销这一例外：子进程失败就意味着门禁失败，即使合并后的覆盖率通过也是如此。

## 后果

分区需要为每个子进程支付一次 Vitest 启动开销，并执行一次报告合并。输出可能交错，分区标签与 Vitest 文件标识可确定其来源。CI 使用完整套件覆盖率；显式分区运行可能因独立分片未覆盖完整源码清单而失败。

并发调优必须依据固定配置下已完成的运行。仅凭进度缓慢，不足以增加进程数量或重启测量。
