# Agent Note: Mutation testing as the coverage counterweight

Status: implemented

[English](2026-06-11-mutation-testing.md) | 中文

## Problem

逐文件 100% 覆盖率门禁（[质量门禁决策](../process/2026-06-11-quality-gates.zh.md)）证明每一行代码在测试中都被*执行*了，但不能证明如果该行出错，任何断言会注意到。在 agent（智能体）编写测试的场景下，覆盖率压力可能产出「执行但不断言」的测试。变异测试衡量的正是覆盖率无法衡量的：测试套件是否能*杀死*被刻意注入的缺陷。

## Decision

Stryker 以 Vitest runner 在 `packages/util/*/src` 上运行，配置见 [stryker.config.mjs](../../../../stryker.config.mjs)，通过 `bun run mutation` 调用。

- **范围本身就是棘轮。** 零依赖的 util（工具）层是其他所有包的基础，因此最先纳入；范围随每一层达到其阈值而逐层扩大。
- **测试套件与变异体同范围。** [vitest.mutation.config.ts](../../../../vitest.mutation.config.ts) 只包含被变异包自身拥有的测试。因此，本可被消费方套件杀死的变异体在这里会存活——该范围限定只会拉低分数，绝不会抬高。
- **使用 `coverageAnalysis: 'all'` 而非按测试归因。** 这些套件通过 tsconfig 路径别名找到被测对象，而 Stryker 的按测试覆盖率归因不跟随该别名：它曾把手工施加后确实会让套件失败的变异体报告为存活。
- **`break` 比已记录分数低不到一个变异体，且只升不降。** 该范围实测 96.57——在 816 个可达变异体中杀死 781 个、超时 7 个。此处一个变异体值 0.1225 分，因此阈值取 96.5：少杀死一个即为 96.45，运行失败。

## What the survivors are

这 28 个存活体并非缺失的断言，而是任何针对公开结果的断言都无法触及的变异体；正是这一区分让该数字保持有意义：

- **内存有界、输出相同。** `TextRetainer` 的后缀裁剪把累加器限制在 `suffixCap` 内。其自身注释已记录 `finish()` 从不读取最后 `suffixLen` 字节之前的内容，因此移除或反转该裁剪只改变内存分配，调用方无法观察到任何差异。
- **构造上即为 no-op。** `clearTimeout(undefined)` 什么也不做，第二次 `[Symbol.dispose]()` 什么也不做，`mkdir({ mode: undefined })` 就是平台默认值。被清空的 `catch` 也属于此类：它返回 `undefined`，而调用方只判断真假值，因此那句显式的 `return false` 表达的是意图而非行为。
- **被其后的检查所涵盖的守卫。** UTF-8 扫描器的边界守卫与其后的序列长度判断重复；`abbreviateHomePath` 中三个此类守卫确属冗余，已直接删除而非加注释排除。
- **限制的是工作量而非输出。** UTF-8 扫描器的回扫上限防止把一长串 continuation 字节从头走到尾；它走多远对返回值不可见。但回扫从哪里停下并非不可见：让它提前一个字节停住，会删掉一个本应由解码器替换的孤立前导 continuation 字节，并使那个由「实际保留的字节」推导出的省略计数偏小——因此那条守卫是被测试覆盖的，而不是被解释掉的。
- **被强制转换，而非抛出。** `RegExp.exec(undefined)` 会针对字符串 `"undefined"` 匹配而不是抛错，因此那条在缺少目标块时提前返回的 LaunchServices 守卫是不可观测的：没有它，下一次匹配同样什么也找不到，调用方无论如何都会回退。

有一条曾在此列的条目是被移出去的，而不是被注解进来的。Windows 的「文件作为父目录」探测看起来像是跨平台限制：POSIX 的 `realpath` 对穿过文件的路径报 ENOTDIR，而该遍历会把除 ENOENT 之外的错误重新抛出；Windows 报的是 ENOENT，因此该探测是那里唯一能拦住它的东西。让 `realpath` 返回 ENOENT 即可在此到达该分支，并杀死它的两个变异体。它钉住的是本 harness 自身的决定——向上走到祖先、打开它、并让失败透出；而断言读到的 errno 来自本机，因此 Windows 对同一调用给出的答案仍只能由一次 Windows 运行来证明。

要把分数提高到这个水平之上，只能删除存活体所在的代码或扩大范围——绝不能排除文件、放宽阈值，或给一个套件本可杀死的变异体加注释。

## What widening can and cannot buy

聚合分数要达到 99，整体存活率必须低于 1%，因此每个新纳入的层级都必须以低于该值的存活率到来，否则它的代价高于贡献：在存活率 `r` 与新增 `N` 个变异体下，需满足 `N * (0.01 - r) >= 22.84`；一旦 `r` 达到 1%，任何 `N` 都无法满足。

两个已实测的范围都高于该阈值。本范围为 3.43%（816 中的 28）。作为第二个范围实测的 `tool-todo` 初始为 12.00%，在补齐测试后达到 4.00%——这些测试钉住了它完整的面向模型描述、参数与输出 schema、`counts.completed`、companion 的插件名，以及跨越一个无关事件的回合边界，共杀死 22 个变异体，每一个都对应着此前无人断言的契约。其余存活者中有四个可证为等价：一个已被状态集合检查涵盖的 `typeof` 守卫、以 `{}` 替代 `{ open: false }`（该字段仅按真值读取），以及 trace 缓存——跳过它只会重新算出同一个 trace。

因此，widening 的上界来自等价变异体的地板，而非测试投入：在低于门槛时纳入某一层级只会拉低数字，而可达到的聚合分数大致为一减去该地板。widening 值得做，是为了它暴露出的缺陷——这正是它在此处换来的东西——而不是作为通往某个被地板挡在门外的目标的路径。

## Alternatives considered

**一开始就变异 `packages/*/src`。** 全仓库范围才是这个分数最终应有的含义，但它不能作为起点：1590 个源文件参与变异、每个变异体重跑一次套件，没有人会等待这样的信号；而首个无人能据以行动的数字什么也教不了。

**用完整套件作为变异测试套件。** 那样每个变异体都会被所有消费方测试检验，杀伤力严格更强，但也意味着每个变异体都要跑 1.7 万个测试；范围限定后的套件约一秒跑完，这正是 820 个变异体可测量的前提。

**给等价变异体加注释并把阈值设为 99。** Stryker 支持禁用注释，上述每个存活体都能附上证明。这只换来一个更圆整的数字，代价是一份后来读者必须重新验证的排除清单，以及每当某个变异体只是「碍事」时就伸手去加一条的长期诱惑。记录真实分数并解释存活体，是更诚实的产物。

**在分数为 95.61 时把 `break` 留在 99。** 无法通过的门禁不是门禁；它只会训练所有人忽略红色的运行结果。

## Consequences

存活的变异体是形态明确的待办项：挑一个、写出杀死它的测试、循环往复。这个闭环把该范围从 82.92 推到 96.57，并为原本没有测试的真实行为补上了测试——UTF-8 切割边界、LaunchServices 解析、临时文件独占创建、变量名大小写折叠、写锁的截止时间与退避，以及抛出的 null 原样到达调用方——外加存活体暴露出的三处代码简化，以及一处收窄的 `try`：它此前会把本包自身的解析失败当作「macOS 无记录」吞掉。

新增该通道把 `docs/testing.md` 的字数上限从 1150 提到 1200：层级列表多了一条通道，且覆盖率层级现在会描述其门禁所承载的各类排除，而不再只提 `pwsh` 一项——旧表述读起来仿佛那是唯一的豁免。

`bun run mutation` 在 `ci-primary`、`ci-linux-primary` 与 `check-all` 中运行，且 `run-gates.spec.ts` 断言了这一归属：无人执行的阈值只是一个数字，不是棘轮。

同一份 spec 还断言该 gate 的标签必须写明它所度量的层级。本范围是仓库 248 个包中的 9 个，因此 CI 中一行 `mutation score` 会让扫过运行结果的人以为那是整个仓库的分数，而通过的并不是它。该标签写作 `mutation score (util tier)`，把未限定范围的旧标签改回去会让该 spec 失败。

尚未构建：记录分数随时间变化的每夜 job，以及在范围足够宽时取代全量运行的 PR（Pull Request）范围增量运行。
