# Agent Note: 为仓库已声明的抑制规则加上门禁

Status: implemented

[English](2026-09-01-suppression-justification-gate.md) | 中文

## 问题

`AGENTS.md` 就"被抑制的检查"声明了两条规则：linter 例外必须窄且有理由；空 `catch` 必须写明它吞掉了什么、以及为什么没有别的东西能到达那里。这两条都没有任何地方去执行。对 250 棵已发布包源码树的普查表明，规则其实是被遵守的——121 处 lint 指令与 89 处空 `catch`，每一处都有理由——但这是逐点人工阅读之后才得出的，既不是评审者可施加的标准，也不是后续改动会自动保持的状态。

## 决策

`scripts/suppression-justifications.spec.ts` 在 `packages/*/*/src` 上运行 `scripts/suppression-justifications.ts` 中的扫描，对没有写明理由的 lint 指令或空 `catch` 判失败。理由的计法有两种：写在规则名之后的 `--` 后面，或写成一整段指令上方的一条注释——`-next-line` 形式的连续段会在指令与它各自标注的那一行之间交替，因此向上行走会跨过两者。含有任何语句的 `catch` 是在处理失败，不在该扫描的管辖范围内。

该扫描会证明自己的拒绝能力：裸指令、裸 `catch {}`、行内理由、成组理由、以及一个真正处理的 `catch` 各是一个用例，因此活的代码树是第二份语料，而不是唯一一份。

有三处为满足它而调整。`region.ts` 去掉了两处 `indexOf` 早已让其多余的断言——`nodes[startIdx]` 就是调用方传入的 `start` seq——并写明了其余每个下标为何在范围内。`testing.ts` 补上了它在 `schema.ts` 中的同类早就带着的理由。`token-meter` 把解释从准备语句上方移到了它所解释的那条指令上方。

## 考虑过的替代方案

**让扫描能找到与指令之间隔着代码的理由。** `token-meter` 原本就是这种形态；把向上行走放宽到能够到它，等于接受任何大致靠近抑制处的注释。把注释移到它所解释的那一行是更小的改动，也是读者能得益的那一个。

**改为在 oxlint 中执行。** 该规则横跨两种互不相关的构造——一条指令注释与一个空块——而空 `catch` 那一半关乎散文，而非被抑制的规则本身。仓库门禁无需自定义 linter 插件即可同时读取两者。

**记录普查结果，规则继续不设门禁。** 普查是干净的，而这恰恰是加门禁最便宜、且永远不必回头去清理积压的时刻。

## 后果

新增的抑制若没有理由，会让 `bun run test` 失败。该扫描是文本性的，因此写得离指令很远的理由会被读作不存在——这正是它所执行的标准，而不是它的局限。
