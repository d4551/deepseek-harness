# Agent Note: 为 floors 看不到的那个方向设一道门禁

Status: implemented

[English](2026-09-02-installable-version-gate.md) | 中文

## Problem

有两道门禁把技术栈往下压住。`verify-toolchain-floors` 拒绝根清单中工具链固定版本低于所声明 major/minor 的情况，`live-stack-floors` 对编译与客户端栈做同样的事。两者都能抓住降级——而降级正是一次协同编辑可以造成、同时其余门禁全绿的那种失败。

两者都抓不住相反方向的漂移。以今天所安装版本写下的 floor 今天是对的，一年后就在无声中变成错的：没有任何东西把这两张表与 registry 已发布的版本作比较，于是每一个固定版本都可以任意落后，而 `check-all` 全绿。这些 floor 的存在是为了阻止技术栈腐化，却看不见它真正腐化的方式。

## Decision

`verify-installable-versions` 会在某个依赖落后于本工作区当下就能安装的版本时失败，并与那两道 floor 门禁一起在 `check-all` 中运行。

报告来自 `bun outdated`。直接询问 registry 意味着要重新实现范围解析、工作区过滤，以及 `bunfig.toml` 里的 `minimumReleaseAge` 阻挡期，而得到的答案会与 `bun install` 的实际行为漂移；这三件事包管理器本来就都知道。

被阻挡期扣住的版本会被报告出来但仍然通过。那道阻挡期是本仓库的供应链策略，因此对它失败会让「变绿」必须以绕过它为前提——门禁反倒在要求一次安全倒退。

该检查读的是最新已发布版本，而不是 `bun outdated` 的范围内 `Update` 列。精确固定的依赖，其范围内目标恒等于已安装版本，因此针对该列的检查永远不可能触发；先在兄弟仓库里正是这样写的，结果一次故意的降级从它面前通过了。

落地时把 `jscpd` 升到 5.1.1、`knip` 升到 6.34.0。`jscpd` 的升级立刻报出 `run-gates.ts` 中一处 5.0.16 检测不到的十四行克隆：消费构建产物树的那批门禁，在 `check-all` 与 artifact 通道中各列了一遍，于是只加进其中一条通道的门禁会在 CI 里跑而本地不跑。它们现在是一个函数。

## Alternatives considered

**用定时的依赖机器人。** 它开的是 pull request，不会让门禁失败，因此忽略它的分支照样绿着合入。两者是互补的，而其中只有一个是门禁。

**直接读 registry。** 因它必须重新实现的东西而被拒绝：范围、工作区、阻挡期。其中每一项都是门禁答案与 `bun install` 实际行为分岔的地方，而与安装器意见相左的门禁比没有门禁更糟。

**对被扣住的版本判失败。** 那会让供应链阻挡期与这道门禁互不相容，于是唯一变绿的办法就是缩短或绕过阻挡期。

## Consequences

某个依赖发布新版本后，一旦过了阻挡期就会让一道门禁失败，因此升级是被有意识地拿下的，而不是等谁碰巧注意到。这确实多出一个「没人动过的绿色分支自己变红」的理由，而这正是目的所在：另一种选择是固定版本在没有门禁看着的地方烂掉。

这道门禁依赖 registry 可达。在不可达的地方，它会大声失败而不是悄悄通过——这正是一道版本门禁应有的行为。
