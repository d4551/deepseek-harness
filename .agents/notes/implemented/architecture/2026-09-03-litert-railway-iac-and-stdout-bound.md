# Agent Note: LiteRT Railway Infrastructure as Code, and a stdout bound the parse owns

Status: implemented

English | [中文](2026-09-03-litert-railway-iac-and-stdout-bound.zh.md)

## Problem

`deploy/litert/` and `packages/llm/llm-litert/` shipped together in [the original LiteRT route](../feature/2026-09-03-litert-lm-route-and-railway-server.md), and an adversarial read of both found six defects that a schema-valid file and a green unit suite could not catch.

The deployment described itself with `railway.json`, Railway's Config as Code. That mechanism is deprecated: new services cannot opt into it at all, and existing files stop being read on 2026-12-01. Schema validity was irrelevant — a fresh deploy from this directory could not use the file. `deploy/litert/` also had no test or gate of any kind, so nothing checked that the entrypoint binds Railway's injected `$PORT` rather than the CLI default, that the volume mount path matches the image's `HOME`, or that the health check path is one the server answers. The one cross-file invariant that existed was a Dockerfile comment asking a human to keep `ENV HOME` "in step with `deploy.requiredMountPath`". Four of the five `:?` guards in `entrypoint.sh` could never fire, because the image baked `HOME` and all three `LITERT_MODEL_*` variables, while the README claimed each one fails loudly.

In the package, `server.maxStderrBytes` was passed as the byte cap for both stdout and stderr, but stdout is not diagnostic: `registryIds()` parses `litert-lm list` from it to decide which models to import. Lowering the field to trim log volume would silently shorten the registry listing, drop ids out of the retained tail, and re-import gigabytes the registry already held. `registryIds()`'s comment described only a header row, while the command also prints a `Listing models in: <dir>` preamble. And `file` was schema-`required()` on every model, including remote routes, which import nothing and already reject `huggingFaceRepo` for exactly that reason.

The Infrastructure as Code file that replaced `railway.json` then repeated the original defect in a new form: it was unverifiable in this repository. `railway` was in no manifest, so `import { … } from 'railway/iac'` resolved to nothing; no `tsconfig*.json` named `deploy/`, so the file was in no TypeScript program; `.oxlintrc.json`'s type-aware overrides listed `packages`, `apps`, `examples`, `scripts`, and `website`, so it was linted by base rules only; and the new gate matched its source text with regular expressions. A misspelled option — `sizeMb`, `healthcheckTimeoutSeconds` — is accepted by every one of those and rejected by `railway config apply`, after a person has linked a project.

## Decision

**The deployment is described by Infrastructure as Code.** `deploy/litert/.railway/railway.ts` replaces `railway.json`, using the generally-available TypeScript authoring API (`defineRailway`, `project`, `service`, `volume` from `railway/iac`, applied with `npm install railway` then `railway config plan` / `railway config apply`). Config as Code keys with no IaC equivalent are not faked: `builder`, `dockerfilePath`, `requiredMountPath`, and the restart policy are gone, `numReplicas` becomes `replicas`, and the volume is a declared `volume()` resource attached through `volumeMounts` instead of a mount-path assertion. `source` is deliberately omitted so the file owns service settings without claiming the repository connection; the service's Root Directory setting is what points Railway's builder at the sibling `Dockerfile`. This also moves when the file is read: `railway.json` was read from the repository during each deploy, while `.railway/railway.ts` is evaluated by the CLI and applied on demand.

**One constant carries the mount-path invariant.** `MOUNT_PATH` in the IaC file is both the `volumeMounts` key and the service's `HOME`, so the volume and the `litert-lm` registry directory (`$HOME/.litert-lm`) cannot drift within that file. The Dockerfile still bakes the same path for a plain `docker run`, and the equality of the two files is a test assertion rather than a comment.

**The image is model-agnostic.** `LITERT_MODEL_REPO`, `LITERT_MODEL_FILE`, and `LITERT_MODEL_ID` are service variables in the IaC file, not `ENV` lines, which is what makes their guards able to fire: an image built from this Dockerfile refuses to start until a service supplies them. The dead `HOME` guard is removed instead of being kept for symmetry — the image sets `HOME` and a container runtime always supplies one, so no guard on it could ever fire. The README now states exactly that.

**`deploy/litert` has an executed gate.** `packages/llm/llm-litert/tests/deploy.spec.ts` reads the three real files and asserts the invariants that span them: no Config as Code file remains, the IaC mount path equals the image's `ENV HOME` and both uses read `MOUNT_PATH`, the health check path equals the path `LitertServer`'s readiness probe requests for the package's own resolved endpoint, the serve line binds `"${PORT}"` and never the resolved default port, every model variable the entrypoint reads is guarded and absent from the image but present in the IaC env, `PORT` is guarded and not pinned in the IaC env, `HOME` is baked and not guarded, and one replica is declared. It lives in the package's `tests/` because that is what the repository's Vitest include globs run; `deploy/` matches none of them.

**Stdout carries its own validated bound.** `server.maxStdoutBytes` (default `1,048,576`) sizes the retained stdout tail the `litert-lm list` parse reads; `server.maxStderrBytes` (default `65,536`) stays the diagnostic knob. Both are validated `Config` fields with the same positive-integer rule, and the difference is stated where each is declared.

**The IaC file compiles against the package Railway evaluates it with.** `railway` is a devDependency at the repository root, because `bunfig.toml` sets `linker = "isolated"` and `deploy/` holds no workspace: the root is the only manifest whose `node_modules` `deploy/litert/.railway/railway.ts` can reach, and it is also where a deployer's own `npm install railway` would land. `packages/llm/llm-litert` declares the same range for the suite that imports the types. `deploy/litert/tsconfig.json` is a leaf project holding that one file; neither aggregate references it, because deployment description is neither Host nor Client product code and a referenced project may not disable emit, so `packages/llm/llm-litert/tests/deploy.spec.ts` runs `tsc --build --force` on it and the check executes under `bun run test`. The four `.oxlintrc.json` overrides that name `scripts/` now also name `deploy/*/.railway/*.{ts,tsx}`, which is what puts the file under the type-aware rules; `knip.json` lists the same glob as a root entry, because the Railway CLI is the only thing that imports it.

**The gate reads the graph, not the file's text.** `deploy.spec.ts` imports the default export, calls it with `createRailwayContext()` and `project` the way `railway config plan` does, and asserts on the `ServiceNode` and `VolumeNode` that come back: `volumeAttachments[…].mountPath`, the `HOME` literal in `variables`, `deploy.healthcheckPath`, `deploy.numReplicas`, and `config.region`. An option Railway ignores is absent from that graph, and reformatting the file does not move an assertion. The Dockerfile and `entrypoint.sh` halves stay textual, because a Dockerfile and a shell script have no evaluated form this suite can reach.

**The volume still pins no region, and a test says why.** `region` is optional in `railway/iac` — `volume(name, config?)` with `region?: string | null`, defaulted to `{}` at runtime and never read by `validateGraph` — and Railway provisions a volume in the region of the service that mounts it. Pinning one on the volume alone is the cross-region attach Railway migrates with downtime, so the file leaves both unpinned, states the four region identifiers at the call site for a deployer who wants to place them, and the suite asserts the volume pins no region the service does not.

**`file` is posture-aware and symmetric with `huggingFaceRepo`.** Both are import instructions. A supervised route requires `file` and accepts `huggingFaceRepo`; a remote route refuses both, with the reason the package already gave for `huggingFaceRepo` — the route points at a server whose registry it never touches, so either key would read as a promise it cannot keep. Resolution now carries `imports: readonly LitertImport[]` on the local endpoint, so `LitertServer` receives entries whose `file` is present by construction rather than re-checking an optional field.

**The file exports a named `partial`, because an apply otherwise deletes what it does not name.** Railway IaC treats a whole-project authoring file as the complete desired state: omit means delete. This file describes one service and is applied to an environment its deployer owns and may already be using, so without a partial `railway config apply` would remove their unrelated resources. `export const partial = 'litert-lm'` limits omit=delete to the service and volume declared here. This is also the shape Railway's own `railway config migrate --service <name>` writes, because the `railway.json` this file replaced was per-service; the hand migration produced everything that tool would have produced except this. The name is applied state — renaming it after an apply orphans what the old name owned — so `deploy.spec.ts` pins it to the service's own name rather than to a literal.

## Verification

`bun x vitest run packages/llm/llm-litert` — 35 tests across the behavior suite and the new deploy gate. The behavior suite gained a fake subprocess handle that actually applies the spawn spec's `maxBytes` as a tail, so three new cases are behavioral rather than assertions about arguments: a registry listing survives `maxStderrBytes: 8` and re-imports nothing, an undersized `maxStdoutBytes` loses the id and forces a re-import, and the first lifecycle case pins the two caps as separate values on the spawn spec. Config cases cover both remote refusals, the supervised `file` requirement, the resolved import list, and `maxStdoutBytes` validation.

Each deploy-gate assertion was proved failing by breaking the file it guards: restoring a `railway.json`; changing `MOUNT_PATH` away from the image's `HOME`; replacing `HOME: MOUNT_PATH` with a literal; moving `healthcheck` to `/health`; hardcoding the CLI default port in the serve line; binding `127.0.0.1`; adding `ENV LITERT_MODEL_ID` back to the image; deleting a model variable from the IaC env; deleting a guard the entrypoint still reads; pinning `PORT` in the IaC env; removing `ENV HOME`; and raising `replicas` to 3. Every mutation failed exactly the assertion that owns it, and the suite is green again after restoring the files.

`bun x tsx scripts/run-oxlint.ts packages/llm/llm-litert deploy/litert/.railway/railway.ts` — 0 warnings, 0 errors over 7 files.

After the IaC file was brought into a program: `bun x vitest run packages/llm/llm-litert` — 37 tests across two files; `bun x tsc -b deploy/litert --force` — clean; `bun x tsx scripts/run-oxlint.ts deploy/litert packages/llm/llm-litert` — 0 warnings, 0 errors over 7 files; `bun x vitest run scripts/live-stack-floors.spec.ts` — 31 tests, covering the new `railway` root floor.

Six more mutations proved the two new assertions and the four re-based ones. `sizeMB` renamed to `sizeMb` and `healthcheckTimeout` to `healthcheckTimeoutSeconds` each failed only the compile assertion, with TS2561 naming the correct spelling; both passed the previous regex gate untouched. Adding `region: 'us-west2'` to the volume while the service pins none failed only the region assertion. Replacing `HOME: MOUNT_PATH` with the literal `'/elsewhere'` failed only the mount assertion, which no longer depends on the constant being spelled at that site. `healthcheck: '/v1/models'` replaced by the valid alias `healthcheckPath: '/health'` compiled and failed only the health-check assertion. `replicas: 3` failed only the replica assertion. Reformatting `volumeMounts` across three lines — which the previous single-line regex rejected — left the suite green.

The Railway API claims above were re-read at their source rather than taken from the earlier reading. `region` is documented under `## Volumes` in a two-column `Field | Description` table that marks nothing required, and the published `railway@3.11.0` declarations agree: `declare function volume(name: string, config?: VolumeConfig)` over `type VolumeConfig = { sizeMB?: number | null; region?: string | null; … }`. Railway's own Public API reference, which does carry a Required/Optional column, marks `VolumeCreateInput.region` Optional. Both documented `volume(…)` examples pass `region`, which is the likely source of a required reading.

The Railway API was read from the live documentation rather than from memory: the Infrastructure as Code reference for the authoring file path, the `service` and `volume` field tables, and `source` omission; the IaC overview for `npm install railway`, the `plan`/`apply` commands, the parent-directory file search, and the Config as Code deprecation wording and 2026-12-01 cutoff; and the health check guide for the timeout unit and its 300-second default.

That reading missed the `## One file per project` section of the same overview page, which is where omit=delete and the named-partial escape are stated. The partial was added afterwards on a re-read and proved by two mutations: dropping the export failed the new assertion with `expected undefined to be 'litert-lm'`, and misspelling it as `'litert'` failed with `expected 'litert' to be 'litert-lm'`. `bun x vitest run packages/llm/llm-litert/tests/deploy.spec.ts` — 9 tests, green after restoring.

## Alternatives considered

**Keep `railway.json` because it validates.** Rejected: validity is not availability. New services cannot opt into the mechanism, so the documented deploy path would fail for the first person who followed it.

**Keep the mount-path agreement as a comment.** Rejected: the comment already existed and already asked a human to maintain it. A constant plus a test moves the invariant from prose into something that fails.

**Keep the model identity in the image and soften the README instead.** Rejected: which model the service serves is deployment configuration, and baking it is the container equivalent of a hardcoded tunable. Removing the `ENV` lines fixes the dead guards and the model-agnostic image in one move, and only the truly unfireable `HOME` guard is then dropped.

**Put the deploy gate in `deploy/litert/tests/`.** Rejected: the repository's Vitest include globs are `packages/*/*/tests`, `apps/*/tests`, and `scripts`, so a suite there would never run. A gate that does not execute is the defect it was meant to fix.

**Filter `Listing` and `ID` out of the parsed registry ids.** Rejected: matching the CLI's prose is more fragile than admitting two words that cannot cause harm. A model configured under either id would only skip an import the server then fails on, loudly. The comment now describes the output the parse actually sees.

**Register `deploy/litert` in `tsconfig.host.json`.** Rejected, and it does not compile: `oxlint-tsgolint` reports `Referenced project '…/deploy/litert' may not disable emit`, and the alternative — giving a deployment directory an `outDir` — writes build output into `deploy/`. An unreferenced leaf run from the suite that owns the directory checks the same file and executes on the same command.

**Pin `region: 'us-west2'` because every documented example does.** Rejected: the types, the runtime, and the docs table all make it optional, and Railway places a volume in its service's region. A region pinned in a repository-shipped file would be pinned for every deployer, and one whose service runs elsewhere would get the cross-region attach that migrates with downtime.

**Let a remote route keep `file` as documentation.** Rejected as the asymmetry that started this. The plugin cannot verify the claim against a server it does not manage, which is precisely the reason it already refuses `huggingFaceRepo`.

## Consequences

- Deploying this directory is now a local CLI action (`railway config plan`, `railway config apply`) instead of a file the platform picks up during a deploy. The README documents the CLI's parent-directory search and the project-name match.
- The volume is declared with `sizeMB: 4096` and no `region`. The size follows the README's own "twice the file size" rule for the default model and stays under Railway's 5 GB Hobby ceiling; the region is left to Railway rather than guessing one for a global audience, and the README says to match it to the service's region when setting it.
- A remote route configured before this change fails at load, naming `file`. That is the intended pre-release break; the READMEs' remote example no longer carries the key.
- `LitertServerSpec.models` became `imports`, and `ResolvedLitertEndpoint`'s local variant gained `imports`. Both are exported types, so a consumer constructing a `LitertServer` directly updates with them.
- `docs/config-catalog.md` is generated from these config types and needs `bun run gen-config-catalog` re-run. It was left untouched here because the working tree held concurrent edits to other packages' configs, and the generator rewrites the whole file.
- `deploy/litert/.railway/railway.ts` now costs a `tsc` process per run of the deploy suite, roughly 60 ms. That is the price of checking a file no other program compiles.
- `railway` moves on an unpinned `npm install railway`, so the repository's `^3.11.0` and its `ROOT_DEPENDENCY_FLOORS` entry are what keep the compile check measuring the API a deployer's CLI will evaluate. Raising one raises the other.
- `deploy/litert/README.md` documents `npm install railway` and the omitted `region` already; it gained one paragraph stating that an apply deletes unnamed resources and that the `partial` export bounds this.
- The `partial` name is now applied state shared with every environment this file has been applied to. Renaming it is not a refactor: the old name keeps whatever it owned, and the resources reappear as unmanaged.
