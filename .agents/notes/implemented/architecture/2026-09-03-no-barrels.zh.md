# Agent Note: 禁止 barrel 模块

Status: implemented

[English](2026-09-03-no-barrels.md) | 中文

## Problem

转发其他模块符号的模块会掩盖符号的归属。导入路径指向一个模块，声明却在另一个模块里，每个读者都必须顺着转发链才能找到归属者。本仓库有 46 个模块存在这一问题，形式有两种。

其中 67 条语句是星号再导出（`export * from './x.ts'`、`export * as ns from './x.ts'`）。星号发布的接口取决于目标模块当下恰好导出了什么，因此转发模块的读者——以及审阅目标模块改动的人——都无法说出它发布了哪些符号。给叶子模块新增一个导出，会悄悄扩大整个包的公开 API。

另有 33 个模块自身没有任何声明，只为转发而存在。其中一些是包的入口文件，于是 `main` 指向了一个不拥有该包任何行为的模块。

## Decision

两种形式都被拒绝。[`scripts/no-barrels.ts`](../../../../scripts/no-barrels.ts) 扫描 `packages/`、`scripts/`、`apps/` 下每个被跟踪的 `.ts`/`.tsx`，跳过 `lib/` 产物与 `vendor/` 中的上游固定副本，对每处星号再导出报告 `star-re-export`，对每个自身无声明、只做转发的模块报告 `pure-barrel`。[`scripts/no-barrels.spec.ts`](../../../../scripts/no-barrels.spec.ts) 用注入的样例和真实代码树两侧驱动它；`scripts/**/*.spec.ts` 属于 vitest 的默认 include，因此该门禁无需自己的脚本入口即可在 `bun run test` 中运行。

符号从声明它的模块导入。需要跨越包边界的符号获得真实的子路径导出，且其产物文件列入 `files`——即 [`dsh-web-fetch-http`](../../../../packages/web/web-fetch-http/package.json) 用于 `./policy` 的形式。该包同时说明了为什么必须验证产物而非假定其存在：它声明了 `./policy` 子路径，而 `lib/policy.js` 从未被构建，因此该导出从未解析成功。

一个既声明自身 API、又列名转发少量符号的模块不是 barrel。它就是包的 `exports` 映射所指向的模块，门禁不会触发。检测器划的界线是归属而非再导出的数量：自身没有任何声明的模块，对它发布的名字没有归属权。

该规则放在 [packages/AGENTS.md](../../../../packages/AGENTS.md) 中其他模块布局规则旁，而不是根约定文件。它最初写入根文件并使其超出词数上限；`docs/AGENTS.md` 要求先迁移再压缩，而模块布局本就是包级议题。在规则已被压缩两次之后，[scripts/doc-budgets.manifest.json](../../../../scripts/doc-budgets.manifest.json) 中 `packages/AGENTS.md` 的上限从 675 调整为 710 以容纳它。

## Alternatives considered

**禁止全部 `export … from` 语句，包括拥有自身 API 的模块中的具名转发。** 那还涉及 210 个模块中的 751 条语句，并会使包的 `exports` 映射成为发布任何符号的唯一途径——每个包新增数十个子路径导出，且所有跨包导入都要重写。被消除的危害是符号归属无法查找；而拥有自身 API 的模块中的具名转发同时写明了名字与来源，不会造成这一危害。

**只禁止跨边界的星号再导出，包内允许。** 接口无法命名的问题两侧完全相同：转发模块的读者仍说不出它发布了什么，目标模块新增导出仍会悄悄扩大接口。

**依靠代码审查。** 这 46 个模块正是在审查之下累积起来的。没有门禁的规则会重新长回来。

## Consequences

符号的导入路径现在指明其归属者，读者一跳即可到达声明，叶子模块的改动也无法在不显式编辑发布边界的情况下扩大包的公开接口。

代价是跨包发布现在是一个刻意动作：一个子路径导出、产物文件列入 `files`、以及确实产出该文件的构建配置。原本一处转发，现在是三处编辑——这正是目的所在，每一处都写明了什么离开了这个包。

自身不拥有内容的包入口必须获得真实内容，或将 `exports` 映射重新指向拥有该行为的模块，这也暴露出一批声明入口与实际实现已经脱节的包。
