# Agent Note: 多根工作区的指令 touch 与 skill 发现

Status: implemented

[English](2026-09-03-multi-root-touch-and-skill-discovery.md) | 中文

## 问题

附加工作区根目录抵达了指令发现，却止步于基线。`dsh-agent-instructions` 在组装基线时会走遍每个已记录根目录自己的项目链，并以绝对路径显示这些文件，因此另一个根目录中的同名文件不会与主根目录的文件相撞。对账流程对此一无所知。由此产生了两个缺陷。

对账流程把每个目录 scope 都按相对主项目根的形式作键，并用 `join(projectRoot, directory)` 把一个 scope 解回去。附加根目录的 scope 目录是绝对路径，而把一个绝对目录拼接到主项目根上，寻址到的是一条在两个根目录中都不存在的路径。于是每一条附加根目录的指令都是在一条永远不存在的路径上被探测的，因此组装基线的那个前置步骤，会在同一条消息里为它刚刚加载的那个文件渲染出 `Instructions removed:`。新增了第二个文件夹的会话，会看到自己的指令在第一次请求之前就先到达、再被撤回。

嵌套发现只覆盖主根目录。`descendantDirsBetween` 仅以会话 cwd 为准来判断一条被 touch 的路径，因此在第二个检出目录内一次成功的 `read`、`write` 或 `edit` 返回不到任何目录，该检出目录的嵌套 `AGENTS.md` 也就从未加载。它的包含性判断还比较相对路径的前导字符，因此一个名叫 `..foo` 的真实同级目录会被读成一次逃逸——这正是 `dsh-fs-network-drive` 中的 `drivePathOf` 早已修正过的那个缺陷。

`dsh-tool-skill` 向它的三次注册表调用全都传入 `cwd: agent.session.header.cwd`，从不查询会话的根目录集合，因此第二个检出目录的 `.dsh/skills` 与 `.agents/skills` 对 catalog 和 loader 都不可见。

## 决策

**工作区根目录拥有它自己的文件所依据的那些指令 scope 键，在 touch 时如此，在基线时也如此。** `probeScopeInstruction` 把绝对目录 scope 当作发现流程为附加根目录产出的那种形式：直接寻址该目录，并以绝对路径显示该文件。对账流程接收会话的附加根目录，通过共享的 `workspaceRootChain` 把每个根目录自己的项目链加入它的基线 scope，并把每条被 touch 的路径路由到拥有它的那个根目录。从两个根目录都能抵达的同一个目录只被探测一次，因为这两个键寻址的是同一个候选项，而既有的绝对路径去重会保留第一个。

**一次 touch 被路由到包含它的最深的已记录根目录**，遵循 `dsh-tool-lsp` 的 `sessionWorkspaceRoot`。因此，记录在另一个根目录内部的根目录拥有它自己的文件，并按它自己的基线作键的方式为这些文件作键，而不是继承外层根目录的相对形式。相对路径路由到主根目录，也就是模型书写相对路径所依据的基准；不在任何已记录根目录之下的绝对路径同样路由到主根目录，在那里包含性判断会把它报告为工作区之外，于是它什么也发现不到。

**包含性是一次整段判断。** `segmentsWithin` 切分相对路径并拒绝字面的 `..` 路径段，因此 `..foo` 与 `...bar` 保持它们在磁盘上本来的普通同级名字，而一个绝对结果——win32 在跨盘符时会返回这种结果——则是一次逃逸。

**skill（技能）跨越每一个已记录根目录。** skill catalog 是一份会话范围内的单一列表，而不是逐文件的路由决策，因此这里遵循 `dsh-tool-fs-search` 的 `searchRoots`，而不是语言服务器的逐文件路由：新增第二个文件夹的用户期待该文件夹的 skill 被加载，而此时手上并没有可供路由的文件。`SkillLookupOptions` 在 `cwd` 之外新增 `additionalRoots`，与会话自己的词汇以及 `dsh-agent-instructions` 的发现选项保持一致。`dsh-skill-filesystem` 贡献每个根目录的项目条目，主根目录在先，当多个根目录解析到同一个项目根时只扫描该项目根一次。注册表的收集缓存除 cwd 外还以根目录集合作键，因此共享同一个 cwd 的两个会话不会互相提供由不同根目录组装出的 catalog。`dsh-tool-skill` 从 `sessionWorkspaceRoots` 构建一次查询，供 catalog、loader 工具以及用户显式的 `/name` 调用共用。

来源排名仍按来源种类划分，而不是按根目录划分：根目录顺序只用来打破排名判平的冲突，因此在两个根目录中都存在的名字由主根目录胜出。引入按根目录的排名会让第二个根目录的 `.dsh/skills` 压过主根目录的 `.agents/skills`，而没有任何消费方提出过这个要求。

## 验证

`bun x vitest run packages/context packages/skill` 覆盖：基线中一个附加根目录文件的对账、由附加根目录内的一次 touch 发现的嵌套指令文件、一个被修改和一个被删除的附加根目录文件、三个已记录根目录之间的最深根路由、不在任何已记录根目录之下的一次 touch、主根目录与附加根目录中各自的 `..foo` 目录，以及一个改写了会话 cwd 拼法或重复了主链已覆盖目录的根目录。在 skill 一侧，它覆盖来自第二个根目录的 catalog 与一次加载、该根目录被移除时的 catalog 退役、多个根目录只扫描一次同一个项目根、只指名附加根目录的一次查询，以及两组根目录之间的缓存隔离。每个新增测试在其修复被还原时都会失败。每个被改动的源文件在四项指标上的逐文件覆盖率都保持 100%，`bun run test:snapshot` 回放不变：没有任何录制会话声明附加工作区根目录，因此没有模型可见的输出发生位移。

## 考虑过的替代方案

**让对账流程只覆盖主根目录，并把这个缺口记为一项限制。** 否决：该包的 README 早已承诺了多根发现与由 touch 驱动的刷新两件事，而每一条附加根目录指令被立即撤回是一个缺陷，不是一项缺失的功能。

**为每个附加根目录分配一个相对它自己项目根的 scope 键。** 否决，因为那样两个根目录会为不同的文件铸出同一个相对键，而这正是绝对显示路径存在的意义所要防止的碰撞。

**在 `dsh-tool-skill` 中按根目录逐个调用 `ctx.skills.list` 并合并结果。** 否决：优先级、按层去重与 catalog 缓存都属于注册表，Consumer 一侧的合并会把这三件事重新实现一遍。

**把 `SkillLookupOptions.cwd` 改名为一个根目录数组。** 暂不采纳：该字段被 `dsh-session-controller` 中的宿主 skill catalog 以及本次改动范围之外的应用测试读取，而新增的这个字段已经写明了会话日志本身所记录的主／附加之分。

## 后果

- 只读取 `SkillLookupOptions.cwd` 的提供方仍照常工作，只是覆盖一个根目录；覆盖其余根目录由各提供方自行选用。
- `reconcileInstructionContext` 在每一轮中解析每个附加根目录的项目根。代价是基线发现早已在执行的同一次向上标记遍历，以根目录深度为界，而附加根目录的 scope 键是绝对的，因此重新遍历不会像重算主根目录那样让已记录的键发生漂移。
- `ctx.remote.skills` 背后的宿主 skill catalog（`packages/api/session-controller/src/skill-catalog.ts`）仍然只为会话 cwd 列出可供用户调用的 skill，因此在那次调用传入会话的根目录集合之前，Web 客户端中面向人的 `/name` catalog 仍然只覆盖主根目录。agent（智能体）内部面向模型的 catalog、loader 与用户显式调用则全都覆盖每一个根目录。
