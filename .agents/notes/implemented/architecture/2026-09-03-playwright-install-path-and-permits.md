# Agent Note: Redirect hops pass the fetch destination policy, on the channel that reports them

Status: implemented

English | [中文](2026-09-03-playwright-install-path-and-permits.zh.md)

## Problem

The rendered fetch route claimed, in five places, that it validates "each redirect hop": the composition comment in `packages/bundle/base/cordis.patch.yml`, `src/policy.ts`'s module and class docs, `src/provider.ts`'s module doc, and two README paragraphs. The only evidence was a unit fake named `redirectHop` handed a loopback URL, which proves the handler refuses loopback and nothing about redirects.

Measured against live Chromium 1.62.1, the claim was false. A page navigated to a URL that answers `302` reaches the target, and `context.route` is invoked for the first hop only — the browser follows a redirect inside its own network stack. `route.fulfill` with a `3xx` status does not produce a followed redirect either; the navigation hangs. The exposure is concrete: a page admitted at a public host, redirected to `http://127.0.0.1:<port>/internal`, loads that origin's content and this provider serializes and returns it. That is the shape a `web_fetch` SSRF takes.

Two other defects travelled with it. `chromiumInstallCommand()` resolved `playwright/package.json` unguarded, and the plugin called it inside the branch a missing `playwright` produces: `resolveAvailability()` swallowed the `ERR_MODULE_NOT_FOUND` from `await import('playwright')`, then the warning re-triggered the same failure synchronously and rejected `apply`, taking the whole profile down. `playwright` is a peer dependency and ships no postinstall — its manifest has no `scripts` field at all — so nothing installs the browser this route needs, and the deployment that hits that path is exactly the one the guidance was for. Separately, `RenderPermits` in `src/provider.ts` was a hand-rolled bounded FIFO admission controller written three days after `@deepseek-ai/dsh-capacity-gate` shipped as exactly that; the clone detector is textual and could not see it.

## Decision

**A redirect hop passes the same policy, decided on the channel Chromium reports it on.** The same measurement that found the gap found the fix: the hop arrives as a `request` event on the context, carrying `redirectedFrom()`, and every hop of a navigation chain is reported *before* `goto` resolves. `RenderContext` gained `on('request', listener)`, and `guardContext` now installs three checks rather than two — the request observer first, because it is synchronous and is the only channel a hop reaches at all. `auditRedirects(policy)` starts a `policy.admit` for every reported request whose `redirectedFrom()` is non-null and skips the rest, because a request the page initiated already reached the interceptor. The hops share the fetch's per-hostname memo, so a redirect back to a host the main frame decided costs nothing.

**A refused hop fails the whole fetch, between navigation and serialization.** `render` settles the audit after `goto` and before `page.evaluate`, so a refusal returns the policy's own `WEB_BLOCKED_URL` and no byte of the document is read. Aborting the single request instead would be theatre: by the time Chromium reports the hop, the page already holds that hop's response, and the bytes would still be in the DOM this provider is about to serialize. What this does not do is prevent the request — the decision lands after the browser issued it, so a blind request to the refused address still happens. Preventing that needs manual redirect following through `route.fetch`, which moves every request a rendered page issues off Chromium's network stack and changes what `page.url()` reports; it is deferred and recorded in the README beside the residual gap it would close.

**`fetchProvider: playwright` stays the shipped route, and the browser step is stated where a deployer meets it.** With hops checked, the destination argument for `http` is gone: both routes now validate every destination, and only the pinning difference remains. Nothing installs Chromium, and a postinstall browser download is not a default this repository has evidence for — so instead of hiding the requirement, `packages/bundle/base`'s README states it in its own `### Install the browser the fetch tool needs` section and again under its known limitations, in both languages: the command, and that every `web_fetch` fails with `WEB_PROVIDER_CONFIGURED_UNAVAILABLE` until it is run. The composition comment carries the same warning at the row that pins it.

**A missing `playwright` yields guidance instead of a crash.** `playwrightInstallCommand(resolve)` takes the module resolver and answers an unresolvable `playwright` with `npm install playwright && npx playwright install chromium`; `chromiumInstallCommand()` binds it to this package's own resolution. The fallback names the package as well as the browser, because the failure that reaches it is the failed import — the browser alone would not help. The injected-resolver shape matches `probeExecutable(locate)` / `probeChromium()` beside it, so the branch a deployment reaches is one a test can reach.

**`RenderPermits` is deleted in favor of `CapacityGate`.** The provider holds a `CapacityGate(limits.maxConcurrentRenders)` and takes its slot through `admitRender(signal)`, which calls `signal.throwIfAborted()` before `acquire(signal)`. That pre-flight check is the one behavior the gate deliberately leaves to its holder: `acquire` grants a free slot without reading the signal, and this provider must open no browser context for a fetch whose budget is already spent. The returned `CapacityRelease` is idempotent, replacing the separate `release()` call. `assertPositiveInteger` now tests `Number.isSafeInteger`, so a cap outside the gate's range still fails with the plugin's own message rather than the gate's `RangeError`.

## Verification

`bun x vitest run packages/web packages/bundle/base` — 26 files, 417 tests, all passing; the playwright package alone runs 62, ten of them against a real Chromium.

The redirect fix is proven end to end against a live browser. `fails the whole fetch when a rendered page is redirected to a private address` launches Chromium with `--host-resolver-rules=MAP fixture.test 127.0.0.1`, serves a loopback fixture whose `/start` answers `302` to `http://127.0.0.1:<port>/internal`, and drives the real `PlaywrightFetchProvider`: the fetch rejects with `WEB_BLOCKED_URL` naming `127.0.0.1`. The launch-time host mapping is what makes an offline render legal at all — the policy refuses loopback, so a fixture page needs a name it will admit — and the redirect target is an IP literal, decided from the literal with no resolver involved. `reports a redirect hop to the request observer and to no interceptor` keeps the platform fact underneath: both hops arrive as requests, only the first is routed, so a Playwright release that starts routing redirect hops turns it red.

Both were confirmed as true positives: with the two-line audit check removed from `render`, all three redirect tests fail, and the real-Chromium one fails by *resolving* — that is, by returning the loopback origin's content to the caller, which is the defect itself.

`names the package as well as the browser when playwright itself is missing` drives `playwrightInstallCommand` with a resolver that throws Node's `MODULE_NOT_FOUND` and asserts `chromiumInstallCommand()` never throws, which is what keeps `apply` total. The fixture in `policy.spec.ts` that was named `redirectHop` is now `loopback`, because that is what it proves.

Per-file coverage over `packages/web/web-fetch-playwright/src` is 100% for statements, branches, functions, and lines across all five files, with no `v8 ignore` comment and no `vitest.config.ts` exclusion. `bun run test:snapshot` passes (107 passed, 2 skipped). `scripts/no-barrels.ts`, `scripts/verify-export-jsdoc.ts`, `scripts/no-duplication-overrides.ts`, `run-oxlint.ts packages/web`, and a scoped `tsc -b` over the five affected packages all pass.

## Alternatives considered

**Leave the hop unchecked and route the base bundle to `http` instead.** Rejected. It was the first answer here, and it was wrong: the only durable argument for it was that `http` validates every redirect hop and the rendered route did not, which is an argument for fixing the provider, not for abandoning the capability. A rendered route is what the deliverable asks for, and the information the policy needs was already being reported on a channel nothing was reading.

**Abort the refused hop's request instead of failing the fetch.** Rejected: the hop is reported after the browser issued it and after the page received the response, so aborting one request leaves its bytes in the DOM the provider is about to serialize. Failing closed is the only outcome that keeps the content from the caller.

**Follow redirects inside the provider through `route.fetch` and fulfil the final response.** Deferred, and recorded in the README as the way to close what remains. It is the only design that prevents the request rather than the disclosure, but it moves every request a rendered page issues off Chromium's own network stack — caching, streaming, and binary bodies included — and `page.url()` would no longer report the final URL, which is a model-visible result field.

**Validate every reported request rather than only the hops.** Rejected: the route interceptor already decides the requests a page initiates, and it aborts a refused one without failing the fetch. Feeding those through the audit as well would turn any page embedding a private-address subresource into a whole-fetch failure, and would duplicate a decision at a strictly worse point in time.

**Install Chromium from a postinstall so the composition installs what it pins.** Rejected: it puts a browser-sized network download into every install of `dsh-base`, breaks offline and air-gapped installs, and commits every deployment to a cost only this route needs. A required manual step stated in the bundle's own README, in the composition comment, in the mount warning, and in every launch failure is honest; a silent one is not.

**Keep the `does not route the hop a redirect names` case as the whole redirect evidence.** Rejected once the gap was closed: it documents a platform fact, not this provider's behavior. It is kept as the negative control beneath the end-to-end case, so the two mechanisms cannot silently disagree.

**Keep `RenderPermits` because the gate's abort semantics differ.** Rejected after checking the one real difference: `CapacityGate.acquire` grants a free slot without reading the signal, where `RenderPermits.acquire` refused an already-aborted caller. That is a holder-level rule the gate documents as the holder's own, and `admitRender` states it in three lines. The rejected error text differs too — `signal.reason` rather than a fixed string — but `renderFailure` translates on the signal's abort state and never reads that message, so nothing model-visible changes.

**Give the rendered route a recorded-session lane.** Rejected: a fixture page it may fetch needs Chromium's launch-time `--host-resolver-rules` mapping, which a shipped profile has nowhere to state, and merely leaving the row mounted makes any scenario host-dependent — the plugin warns at mount exactly when the host has no Chromium, and the headless harness compares process stderr byte for byte. The composition header in `snapshots/session/web-fetch/cordis.yml` and the README both record that, where a reader who wonders why the row is disabled will meet it.

## Consequences

- A rendered page that is redirected to a loopback, link-local, or private address fails the fetch with `WEB_BLOCKED_URL`, and nothing it read is returned. The request to that address is still issued; that residual is named in the README rather than papered over.
- The provider now depends on three Playwright channels rather than two. A future release that changes which channel reports a redirect breaks the audit, and the real-Chromium negative control is what says so.
- `web_fetch` on a host that has not run `playwright install chromium` still fails — but the step is stated in the base bundle README's own section and limitations, in the composition comment, in the mount warning, and in every launch failure, in both languages.
- A deployment that mounts this plugin without `playwright` now boots, and its warning names a command that installs the package and its browser together.
- `dsh-web-fetch-playwright` gains `@deepseek-ai/dsh-capacity-gate` as a peer and dev dependency plus a tsconfig reference, and drops 42 lines of admission control it owned and tested itself.
- Superseding detail for [the WebSocket policy note](2026-09-03-playwright-websocket-policy-and-coverage.md): its claim that `RenderPermits.acquire` keeps `browserOrRelaunch` unreachable after abort now rests on `admitRender`, which performs the same refusal; and its statement that every request a rendered page issues passes the interceptor was true only of the requests a page initiates.
