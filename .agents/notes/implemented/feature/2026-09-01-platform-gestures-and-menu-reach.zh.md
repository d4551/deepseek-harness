# Agent Note: 行列表中的平台手势与可达性

Status: implemented

[English](2026-09-01-platform-gestures-and-menu-reach.md) | 中文

## Problem

Workspace 的行手势（[手势笔记](2026-08-31-workspace-row-context-menu-and-range-archive.zh.md)）及其键盘计数（[键盘笔记](2026-09-01-workspace-row-keyboard-account.zh.md)）在读取指针时，当作所有主机都以同样方式支配按键，并且有三处可达性没有达到它们自称实现的模式。

Apple 平台以次级菜单应答 Ctrl 点击。WebKit 会为那次按压同时派发 `click` 与 `contextmenu`，因此把 Ctrl 读作范围增删修饰键的行，会在同一个手势里既切换该行又打开它的菜单；而那次按压发出的 `contextmenu` 报告的是主按键，于是行把一次光标按压读成键盘请求，把菜单锚定在行上而不是光标处，并在操作者手下把焦点取走。

搜索结果声明了 `role="tree"`，渲染出来的却是普通按钮：每条结果各占一个 Tab 停靠位，方向键在那里毫无作用，也没有任何行报告层级。五十条匹配结果要按五十次 Tab 才能越过。

`Menu` 用原生属性禁用不可用的条目，这会把它们完全排除在焦点顺序之外；方向键跳过它们，读屏软件也从不念出它们。菜单模式的要求恰恰相反——不可用的条目可获得焦点，并拒绝自身的激活。

折叠分组持有的 **Show N more** 行原本是 `role="tree"` 内的一个普通按钮：既不是 `treeitem`，又自成一个 Tab 停靠位，因此五个折叠分组的侧边栏在一份只承诺一个停靠位的列表里要占去六个。它与搜索结果都没有画自己的停靠位焦点环，于是退回到页面那圈向外的焦点环，而一个会滚动、因而在两个轴上都会裁剪的列表，会把它在边缘处切掉。行级无障碍审计看不到这些——它在手工搭起的 `tree` 里只渲染一行，从不渲染组装好的区域。

两棵树都不应答可打印字符。树模式要求任何超过少数几行的树提供 type-ahead，而会话侧边栏正属此列：没有它，要到达往下第五十行就只能按五十次方向键。

停靠位的焦点恢复在第一次方向键时就锁上，之后再也不会解锁。从那时起，任何一次发现焦点落在 body 上的校正都会把焦点拉回列表，哪怕操作者早已离开侧边栏去了别的控件、而那个控件自己消失了。

## Decision

`packages/client/ui-workspace/src/client/pointer-platform.ts` 持有这两项平台读数，按手势逐次从 `navigator.platform` 读取，因此测试可以指定主机。`additiveModifier` 在 Apple 平台上是 Cmd，其他平台上是 Ctrl——它既回答增删单行的那次点击，也回答取走整份计数的那个 A，这是一条平台规则，因此只有一处归宿；`secondaryPress` 在任何平台上读按键号 2，外加 Apple 的 Ctrl 点击。`useRowMenu` 依 `secondaryPress` 决定菜单的锚定与焦点。那次按压另外派发的 click 不再靠平台判定，而是靠行本身已经持有的信号来吞掉：`selectionTookClick` 拒绝任何在本行菜单开着时到达的 click。这与任何一个列表开着时 click 所遵循的规则相同——按压关闭列表，对行不做任何事——并且在 `navigator.platform` 误报的主机上同样成立，因此没有哪个主机能对一次按压作出两次反应。

搜索结果采用与两个会话列表相同的游走停靠位，由 `SearchResults` 中的 `useRowFocus` 提供。每条结果报告 `aria-level`、自己的键，以及列表唯一的 Tab 停靠位；方向键与 Home/End 移动它，Enter 打开获得焦点的结果。它们只有一层且其上没有范围，因此 Shift 不带走任何东西，Space 保留页面滚动，而结果行以 `aria-current` 报告打开的 Session，不再承诺任何范围都产生不了的选择状态——会话行对范围触及不到的行早已遵守这条规则。

这一切由同一个停靠位构造器承担。`rowSeat` 接收行能够携带的范围本身，而不是一个说明它能否携带的标志：没有范围的行什么都不传，这是一个信号而不是必须彼此吻合的两个；搜索结果也与其他每一行经由同一次调用构建自己的停靠位。

溢出行与其他每一渲染行一样在所属列表的计数中占一个停靠位，并以它所揭示的会话的深度渲染为 `treeitem`。它不带 `aria-expanded`：在树行上，该属性承诺的是该行自身拥有的子节点，而这一行揭示的那些行是它的兄弟。它的标签已经说明了下一次激活的方向。它的导航按键走的是两种行共用的那个 `rowKeyDown`，后者会连同取消 Enter 的默认行为一起处理，因此该行只打开一次而不是两次；Space 在那里不被应答，保留浏览器本来就给按钮的激活行为。没有范围能触及它，条件与 Ungrouped 分组头相同。

两种行如今都画上与会话行相同的内嵌焦点环。

不带命令修饰键的可打印字符按标签搜索列表。`useRowFocus` 在 `TYPE_AHEAD_MS` 内收集这些字符，并把停靠位移到下一个标签以它们开头的行，绕过列表头部回环；只有一个字符的缓冲从发起搜索的那一行之后开始查找，因此重复某个字符会在以它开头的各行间走动，而更长的缓冲从该行本身开始，持续细化它。行在已公布的键旁边把自己的标签公布为 `data-row-label`，理由与焦点依属性移动相同：发起搜索的行够不到它的兄弟节点，而列表拥有它们渲染进去的那个元素。type-ahead 只移动焦点——它点名某一行，而不是横扫其间的各行，因此没有范围可带。

`Menu` 以 `aria-disabled` 而非原生属性标记不可用的条目，让每个条目都留在方向键环里，并在条目自身的处理器中拒绝激活。这样的条目也不再打开子菜单、不再声明弹出层，因为它永远无法展示的嵌套卡片并不是一项可用能力。`Menu.module.css` 依该属性为不可用条目设定样式，`tests/menu-styles.client.spec.ts` 钉住这层耦合——jsdom 不应用任何 CSS module 规则，因此若样式表仍依据条目已不再携带的 `:disabled` 状态，别处不会有任何察觉。

`useRowFocus` 改用 document 上的监听器观察焦点是否在自己的列表内，而不是在第一次移动时上锁。`focusin` 交代焦点落在了哪里。`focusout` 只在被 blur 的元素仍在文档中时才放弃恢复——那是操作者主动放下的焦点——因为离开的行会把焦点带走，浏览器报告那次 blur 时该行已经脱离文档，而在 jsdom 下则根本不报告。恢复本身在每次渲染之后都会检查，而不只在停靠位变化时：焦点可能落在方向键从未到访过的行上，而归档那一行不会改动已校正的停靠位。

## What the pattern still leaves out

两棵树都遵循树模式中不依赖修饰键的选择模型：Space 切换获得焦点的行，Shift 与方向键或 Space 组合带走范围，平台的增删修饰键加 A 则一次取走整份计数，并锚定在它的头部，好让随后的 Shift 移动从那里收窄。`Ctrl+Shift+Home`/`End` 不在此列：它们要建立的范围，正是 Shift 与方向键已经在逐行建立的那一个，而锚点刚刚由全选设定。

从范围触及不到的行——Ungrouped 分组头、临时的空白草稿、折叠分组的溢出行——按下 Shift 只会移动焦点而不带走任何东西，因为这样的行不在计数之内，也就无法为计数的某个切片充当锚点。Shift *跨过*这样的行则一如既往地带走范围：计数依据是可见的阅读顺序，而不可触及的那一行两侧的行在其中仍是相邻的。

## Alternatives considered

**连伴随的 click 也去问平台。** 已否决：平台读数对锚定位置而言足够好——读错的代价是菜单锚在行上而非光标处；对安全性而言则很差——读错的代价是操作者从未要求过的一次范围编辑。行自身开着的菜单精确回答了安全性问题，且完全不需要任何读数。

**在模块加载时读取一次平台。** 已否决：那样读数在整个进程内固定不变，测试只能通过重置模块来改变它。按手势读取在一次点击上只多一次属性访问。

**通过 `navigator.userAgentData` 检测 Apple 主机。** 已否决：本仓库编译所依据的 TypeScript DOM 库并未声明它，而 Safari——那个 Ctrl 点击会多派发一个 `click` 的浏览器——并未实现它，因此类型断言换不来任何东西。`navigator.platform` 虽已弃用却处处可答，而修饰键约定正是 MDN 至今仍为它记录的用途。

**在所有平台上都把 Cmd 或 Ctrl 当作增删修饰键，让行菜单获胜。** 已否决：在 WebKit 上两个手势仍会一起跑，于是范围里多出一次操作者从未要求的切换，右击所在的那一行被随意地选中或取消选中。

**沿用搜索结果原先的 `tabIndex={0}` 行。** 已否决：那正是游走停靠位要消除的五十个 Tab 停靠位的侧边栏，而一个声明了 `role="tree"` 却不应答任何方向键的列表，比什么都不声明更糟。

**保留原生 `disabled`，并在方向键环中跳过不可用条目。** 已否决：操作者由此无从发现该条目存在、也无从得知它为何不可用，而这正是该模式让它保持可获得焦点的全部理由。

**在把溢出行提升为树行之后仍保留 `aria-expanded`。** 已否决：它在普通的展开按钮上读起来正确，在 `treeitem` 上则不再正确——那里它宣告了该行既没有的子节点、也没有的展开按键。

**让溢出行保持按钮身份并移出 Tab 顺序。** 已否决：给一个别处无从到达的控件加 `tabIndex={-1}`，会让它对键盘完全不可达，比多一个游离的 Tab 停靠位更糟。它按位置和按动词都属于该列表的一行，因此也属于该计数的一行。

**用行渲染出的文本来匹配 type-ahead。** 已否决：一行的文本是标题加上它的状态与相对时间，因此搜索会像应答会话名一样应答“3”和“进行中”。行公布的标签才是操作者要找的那一个字符串。

**在任何不带 relatedTarget 的 `focusout` 上清除焦点读数。** 已否决：在浏览器中，被移除的行发出的 blur 正是这个形状，因此清除恰恰会在恢复机制所针对的情形下触发。被 blur 的元素是否仍在文档中把两者区分开来，读数也就撑过了它必须撑过的那次移除。

## Consequences

Apple 主机上的 Ctrl 点击会在光标处打开行菜单且不做别的，Cmd 点击编辑范围；其他主机仍以 Ctrl 编辑范围、以自身的次级按键打开菜单。搜索结果只花一次 Tab，并应答方向键。范围触及不到的菜单条目会被念出并被拒绝，而不是从键盘前隐去，这改变了每个 `Menu` 使用方从 `hasAttribute('disabled')` 得到的结果——原先断言它的两处改为断言 `aria-disabled`。折叠分组的溢出行不再占用自己的 Tab 停靠位并且应答方向键，这把它对任何查询而言的角色从 `button` 改成了 `treeitem`。任意长度的行列表都能通过键入其行名到达。操作者移出行列表的焦点会留在他们放下的地方。

覆盖：`tests/pointer-platform.client.spec.ts` 在 Apple 主机、iPad 与 Windows 主机上钉住两项读数；`tests/rows.client.spec.tsx` 端到端钉住 Apple 的 Ctrl 点击——列表在光标处打开、焦点留在行上、伴随的 click 什么也不编辑、列表消失后 Cmd 才切换——钉住在任何开着的行菜单之下的 click 只会关闭它而不对行动作，钉住搜索行的停靠位、层级、键，以及它有 `aria-current` 而无 `aria-selected` 的状态，并钉住全选取走整份计数、在计数之外的行上拒绝作答、以及连同取消浏览器自身的全选；`tests/browser-styles.client.spec.ts` 钉住停靠位所能落到的每一行都把焦点环画在自身内部——这是列表在两个轴上都会裁剪所要求的；`tests/workspace-browser.client.spec.tsx` 钉住渲染出的结果列表上只有一个 Tab 停靠位、移动它的方向键、在组装好的树上走动的一次 type-ahead、在分组列表与扁平列表中都仅凭键盘全选并归档每一个可触及 Session、在展开的项目同时把答应该 Session 的分组头与它自己的行放进计数时只计一次、溢出行的停靠位、它缺席的 `aria-expanded` 与单次激活，以及对组装好的区域在分组态与搜索态两种情形下的无障碍审计——行级审计无法代替的那一份；`tests/row-focus.client.spec.tsx` 钉住获得停靠位的行离开时的恢复、焦点落在停靠位从未到访过的行上时的恢复、对已移出列表或被操作者主动放下的焦点拒绝收回，以及 type-ahead 的落点、重复走动、细化、缓冲窗口与未命中时的保持；`packages/client/ui-primitives/tests/atoms.client.spec.tsx` 钉住不可用条目的可获得焦点、它的拒绝、它不打开的子菜单，以及如今把它包含在内的方向键环。
