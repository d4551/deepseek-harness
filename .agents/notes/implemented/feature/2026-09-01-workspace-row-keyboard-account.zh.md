# Agent Note: 工作区行计数的键盘可达性

Status: implemented

[English](2026-09-01-workspace-row-keyboard-account.md) | 中文

## Problem

行内右键菜单与范围归档（见[手势笔记](2026-08-31-workspace-row-context-menu-and-range-archive.zh.md)）交付时只是指针的工作。行是没有 Tab 停靠位的 `role="treeitem"` 元素，而一行的尾部操作项——**...** 按钮也在其中——在指针悬停之前都是 `display: none`，这同时把它们排除在 Tab 顺序之外。因此没有指针的使用者既够不到行菜单，也够不到范围选择：侧边栏整个浏览区域不过是一串按不到的隐藏按钮。范围施加在项目分组头上的标记同样没有对应的样式规则，于是落入范围的项目虽带着 `aria-selected` 和相应的类，却什么也没画出来。

## Decision

每个列表在其范围选择已经使用的那份有序计数之上持有唯一一个游走的 Tab 停靠位，由 `packages/client/ui-workspace/src/client/row-focus.ts` 中的 `useRowFocus` 持有。该停靠位与选择完全一样，在读取时对照已渲染的键做校正，因此被归档、被折叠或被过滤掉的行会把停靠位交还给计数的头部，无需另跑一趟。行把自己的键以 `data-row-key` 公布出来，列表则依这个属性移动焦点：停靠位要在发起移动的那一行够不到的兄弟节点之间穿行，而列表本就拥有它们渲染进去的那个元素。计数之外的行——Ungrouped 分组头、临时的空白 **New Session**、以及搜索结果——都留在 Tab 顺序之外，因为它们没有任何按键能够触及的操作项。

`RowMultiSelection` 把停靠位与选择一并携带，于是一个 prop 就描述了某一行在其列表中的完整切片，指针与键盘通过同一组动词编辑同一个集合。`Rows.tsx` 中的 `rowKeyDown` 负责路由两种行共有的按键：方向键与 Home/End 移动停靠位，Shift 让范围随移动一同延伸，Space 在 Ctrl/Cmd 点击的位置增删获得焦点的那一行，Shift+Space 取走范围，Enter 则确定锚点并做普通点击所做的事。左右方向键由每种行各自应答，因为它们对父节点和叶节点含义不同：在项目分组头上，展开方向键会展开折叠的分组、并在已展开的分组上进入第一个子行，收起方向键则将其折叠；在会话行上，收起方向键退回到它所属的分组头。其余按键一律保留浏览器自身的含义，只有被应答的按键才会被取消默认行为。一行只应答属于它自己的按键：尾部的 **...** 按钮自行处理 Enter 与 Space，而行菜单是该行在 React 树中的子节点，其采用 portal 的列表会沿 React 树冒泡回来——若不作此判断，方向键会同时走开着的菜单和它下面的列表。

键盘上的范围需要一个锚点，而指针天然就有一个——shift 点击之前必定有一次设定了锚点的普通点击。因此 `RowSelection.extendTo` 同时说出手势的起点与终点：shift 点击传入指针下的那一行，Shift+方向键传入焦点离开的那一行，而已开启的范围保留它已有的锚点，于是连续按下的一串 Shift+方向键从范围起始处生长，而不是从每次按键离开的那一行。

Shift+F10 与 ContextMenu 键抵达行的方式与右击相同，都是那个 `contextmenu` 事件，只是背后没有指针按键，因此 `useRowMenu` 直接读这个事件，而不是新增第二条路径。只有次要按键会报告按键号 2，也只有它带着值得尊重的位置，因此唯有它把菜单锚定在光标处；其余情形——两个菜单键与触摸长按——一律锚定在行上。只要是键盘发出的请求，菜单就通过 `Menu` 新增的 `autoFocus` prop 把焦点取走：`contextmenu` 到达时该行原本就持有焦点，或者尾部按钮的点击不带指针细节——Enter 与 Space 在该按钮上正是这样报告自己的。按压永不索取焦点，因为其操作者并不在列表之中。`Menu` 需要这个 prop，是因为它的列表是文档末尾的 portal——把焦点留在行上，会让页面上其余所有可聚焦元素横在使用者与菜单之间——而焦点一旦落在某个条目上，它便用方向键在自己的条目间移动。行内获得焦点现在以与悬停相同的条件显现尾部操作项，这正是 **...** 按钮得以进入 Tab 顺序的原因；两种行也都带上了范围标记，以及一圈能在其下的选择填充之上仍然可见的焦点环。

## Alternatives considered

**让行保持不可聚焦，把键盘挂在 ... 按钮上。** 已否决：该按钮在悬停之前是 `display: none`，本就不在 Tab 顺序里，无从挂起；而让它常驻显示会让每一行失去静止时的版式。它也没有给方向键提供停靠位，而范围手势恰恰需要它。

**给行加 `tabIndex={0}` 而不是游走停靠位。** 已否决：那样一个有五十个会话的侧边栏就要按五十次 Tab 才能穿过，而树形模式的存在正是为了让一个列表只占一个 Tab 停靠位。游走停靠位也正是范围延伸所寻址的对象——Shift+方向键必须知道它离开的是哪一行。

**把键盘建模为选择之外的另一个行 prop。** 已否决：二者的出现条件完全相同——计数内的每一行两者都有，计数外的每一行两者都无——因此两个 prop 会让调用方得以表达一个不可能存在的状态，而每个手势都得同时判断两者。

**为每个打开的 `Menu` 聚焦第一个条目。** 已否决：指针打开的列表绝不能移动焦点，而那些随指针离开而消失的行菜单会把焦点从使用者正在输入的地方夺走。调用方知道是哪种手势打开了自己的列表，因此该 prop 是选择性加入的，基础组件对指针调用方仍然诚实。

**为这棵树补上 `role="group"` 包裹层与 `aria-level`。** 在此否决：扁平的分组区块本就是这棵树的既有搭法，它不属于本笔记覆盖的任何一种手势，而为满足它去重构已渲染的元素，会牵动拖拽标记与分组间距所依赖的 CSS。它仍是一处已知的缺口，而不是一处无人提及的缺口。

## Consequences

浏览区域进入只需一次 Tab、离开也只需一次，而指针在其中能做的事键盘都能做：走遍这棵树、操作项目的展开状态、打开会话、跨项目建立范围、并从行菜单提交批量归档。屏幕阅读器用户拿到了先前就已许诺的停靠位与 `aria-selected` 标记，另加一圈焦点环——否则选择填充会把光标所在之处遮住。`Menu` 增加了一个选择性加入的 prop 和条目间的方向键导航，现有调用方无需改动即可继承，因为方向键只在焦点已经落在某个条目上时才起作用。

覆盖：`tests/row-focus.client.spec.tsx` 钉住停靠位、被钳制的移动、退回分组头，以及停靠行不再渲染时的回退；`tests/rows.client.spec.tsx` 钉住两种行上的按键路由、Tab 停靠位属性、被排除在计数之外的行，以及每一种菜单来源各自的焦点行为，包括由键盘与由指针打开的尾部按钮；`tests/workspace-browser.client.spec.tsx` 完全用键盘建立并归档一段项目范围，并走遍组装后的树；`tests/browser-styles.client.spec.ts` 钉住两种行都带有该标记、焦点会显现尾部操作项、以及停靠位被画了出来；`packages/client/ui-primitives/tests/atoms.client.spec.tsx` 钉住 `autoFocus`、焦点的交还，以及指针打开的列表对两者都不干预。这棵树扁平的分组结构与缺失的 `aria-level` 仍未被覆盖，因为它们仍未改变。
