# Agent Note: 手机上的侧边栏以抽屉形式覆盖在中栏之上

Status: implemented

[English](2026-09-06-phone-sidebar-drawer.md) | 中文

## Problem

[`columns.ts`](../../../../packages/client/ui-layout/src/client/columns.ts) 写明侧边栏从不让出宽度：所有挤压都由中栏吸收。在 `SIDEBAR_AUTO_COLLAPSE` 之上这成立，在 768 处重新展开也仍能留下 488px 的中栏。低于该断点时这套算术就不够用了。在 Chromium 中针对交付的组合实测：在 375px 展开侧边栏得到 `280px | 95px | 0`——95px 的中栏把问候语裁成"to the / nknown"，把输入框压成一条窄缝，并把模型选择触发器挤到 17×28，低于 CSS 扫描在其他各处都坚持的 24px 目标下限。390px 得到 110px 与 23×28。手机用户从侧栏自身的切换按钮就能进入该状态。

没有任何东西测量过它。其余每个 Web 场景都在 1100 到 1680px 宽之间运行，因此没有任何已提交的测试在小于桌面窗口的尺寸下渲染过这个外壳。

## Decision

`SIDEBAR_OVERLAY` 为 640px。低于该值时，展开的侧边栏被绘制在中栏之上而不占用一列：求解器收到的是关闭偏好，因此网格保留导轨轨道、中栏维持折叠时的宽度，而侧边栏这一列以其抽屉宽度绝对定位，并由一层遮罩覆盖它所遮挡的内容。选择 640 作为边界，是因为 768 仍能留下可用的中栏，而 375 与 390 不能。

每一列都固定到自己的轨道上（`grid-column: 1|2|3`）。否则把侧边栏移出常规流后，自动放置会让中栏滑进导轨轨道——这正是本次改动第一版发生的事：抽屉打开了，中栏报告的宽度也正确，而输入框却被渲染进 56px 之中。探针发现了它，现已提交的场景会对此做断言。

遮罩是一个真正的按钮，携带 `sidebar.closeOverlay`，因此键盘会在抽屉自身控件之后按顺序到达它；它比抽屉低一个 z 层级（`--dsw-z-shell-drawer`），从而遮暗中栏而不是遮暗打开它的那块面板。

## Alternatives considered

**让侧边栏在该断点之下让出宽度。** 否决："侧边栏从不让出宽度"是拖拽钳制与让步链所依据的契约，而在拖拽过程中宽度自行改变，正是该契约要防止的行为。

**把抽屉做成全宽。** 否决：导轨是手机用户返回的途径，而一块背后看不到页面的全宽面板读起来是一个导航页，而不是抽屉。

**提高 `CENTER_MIN`，让求解器拒绝挤压到那种程度。** 否决：求解器的最终兜底之所以存在，正是因为视口可能小于最小值，因此提高下限只是改变数字，并不能消除该状态。

## Consequences

`packages/client/ui-layout` 现在拥有第二个断点，两者都写在 `columns.ts` 中而不是样式表里。把侧边栏驱动到 640px 以下的场景会看到抽屉，而 `apps/web/tests/responsive-shell.e2e.ts` 在 375、768、1024 与 1440 上守住这个外壳：没有横向溢出、没有小于 24px 的可见控件、每个宽度对应预期的轨道，以及抽屉保持中栏宽度。把 `SIDEBAR_OVERLAY` 设为 0 会让该场景失败，这就是该断言被证明的方式。
